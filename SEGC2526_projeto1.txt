1 Objetivos
A parte prática da disciplina de Segurança e Confiabilidade pretende familiarizar os alunos com alguns
dos problemas envolvidos na programação de aplicações distribuídas seguras, nomeadamente a
gestão de chaves criptográficas, a geração de sínteses seguras, atestação remota, cifras e assinaturas
digitais, e a utilização de canais seguros. O primeiro trabalho a desenvolver na disciplina será realizado
utilizando a linguagem de programação Java e a API de segurança do Java, e é composto por duas
fases. A primeira fase do projeto está enunciada neste documento, e tem como objetivo fundamental
a construção de uma aplicação distribuída, focando-se essencialmente nas funcionalidades da
aplicação. Na fase 2 do projeto, iremos dedicar os nossos esforços para garantir que todos os
processos – transmissão de mensagens, salvaguarda de dados, ou execução de software – são seguros
e confiáveis. O enunciado da segunda fase será divulgado oportunamente.
O trabalho envolve a implementação do Sperta, um sistema de casas inteligentes (smart homes) que
permite gerir os seus dispositivos de domótica (smart things). O sistema assenta numa arquitetura
cliente-servidor, como ilustra a Fig.1. A aplicação cliente do Sperta, denominada SpertaClient, permite
a um utilizador se conectar ao servidor e gerir as suas casas inteligentes, ou seja, enviar comandos
para o servidor e receber dados deste. Para o cliente interagir com o servidor, primeiramente o
utilizador terá de se autenticar neste, e posteriormente indicar qual a Casa que pretende gerir.

No servidor, uma Casa é vista como uma estrutura dividida em seções (ver Fig. 2), nas quais são
inseridos os dispositivos inteligentes. As seções são vistas como representações de categoria de
dispositivos (ex., Electrodomésticos, Garden, Luzes, Multimédia,...). Por exemplo, na Fig. 1, o utilizador
iberia gere (i.e., é dono) Casa1 e Casa2. A Casa1 possui dispositivos inteligentes de Multimédia,
Portas e Luzes; Multimédia contém 2 dispositivos: M1 e M2 (ex., M1 é uma TV e M2
um SoundBar); M1 está ligado por 45 min (M1:45) e M2 está desligado (M2:0).
Um utilizador, dono de uma casa, pode dar permissões a um outro utilizador para
gerir seções da sua casa ou mesmo a casa inteira. Por exemplo, na Casa1, o
utilizador alan tem permissões para gerir os dispositivos de Multimédia e Luzes
(alan: M,L). Na Casa2, o utilizador alan tem permissões para gerir toda a
casa (alan:all), enquanto o utilizador nuno os dispositivos de Garden
(nuno:G).
Fig.2. Estrutura de uma Casa no Sperta.
A aplicação SpertaClient tem duas grandes funcionalidades: 1) Enviar comandos para o servidor para
gerir os dispositivos (ligar, ligar com temporização e desligar) e dar permissões a utilizadores; 2)
Aceder à informação sobre o último comando enviado para os dispositivos de uma dada casa, ou
receber um ficheiro de log com o histórico dos comandos enviados a um dispositivo de uma dada casa.
Para fazer uso de todas estas funcionalidades, a aplicação SpertaClient deverá implementar uma linha
de comandos simples, para interação com o utilizador.
A aplicação servidor do Sperta, denominada SpertaServer, permite a ligação com vários clientes em
simultâneo, mantém informação (atual e histórica, na forma de log) sobre os dispositivos, casas e
utilizadores registados, autentica e identifica utilizadores, e vai colecionando e partilhando
informação já recebida dos vários clientes, de forma organizada e persistente. Cada dispositivo tem
um ficheiro de log, no formato csv, o qual contém o seu histórico de funcionamento, ou seja, regista
todos os comandos de operação (ligado, ligado com temporização ou desligado) do dispositivo,
incluindo a data e hora da sua ocorrência.

2 Arquitetura do Sistema
O trabalho consiste no desenvolvimento de duas aplicações:
•

A aplicação servidor SpertaServer (espera ligações TCP)

•

A aplicação cliente SpertaClient (acede ao servidor via TCP)

O servidor deverá poder executar numa máquina e permitir ligar um número elevado de clientes a
serem executados simultaneamente em máquinas distintas. A execução das aplicações deve ser feita
da seguinte forma:
1. Servidor:
SpertaServer [port]
•

[port] identifica o porto (TCP) para aceitar ligações de clientes. Por omissão, o servidor
deve usar o porto 22345 e aceitar ligações em qualquer interface.

2. Cliente:
SpertaClient <serverAddress> <user-id> <password>
Em que:
•

<serverAddress> identifica o servidor. O formato de serverAddress é o seguinte:
<IP/hostname>[:Port]. O endereço IP/hostname do servidor é obrigatório e o
porto é opcional. Por omissão, o cliente deve ligar-se ao porto 22345 do servidor.

•

<user-id> - string que identifica o utilizador no servidor SpertaServer.

•

<password> - string correspondente à password do utilizador.

Servidor
O servidor mantém um ficheiro de texto com os utilizadores do sistema e as suas respetivas
passwords. Este ficheiro deverá ser utilizado quando o cliente se tenta autenticar no servidor.
O servidor mantém um ficheiro de texto com as casas existentes, nomeadamente o seu nome
(Casa1, Casa2, ...) e dispositivos inteligentes que lhe estão associados. Esse ficheiro deverá também
manter a lista de utilizadores que têm permissões de gestão (total ou parcial) de cada casa. Este
ficheiro deverá ser utilizado quando o cliente tenta gerir a casa (i.e., ler dados do servidor ou enviar
comandos para o servidor para gerir os dispositivos de uma casa). Também, o servidor mantém um
ficheiro de texto com os últimos estados/temporizações de cada dispositivo, bem como os ficheiros
de log de cada dispositivo.

O servidor deve atestar a aplicação cliente, ou seja, que a aplicação que estabeleceu conexão com ele
é, de facto, a SpertaClient. Para tal, o servidor recebe o tamanho desta (vindo da própria aplicação
cliente) e o valida com a informação que possui localmente sobre a aplicação. O servidor mantém um
6

ficheiro de texto com o nome da aplicação e o respetivo tamanho (ex., SpertaClient:2734). Se a
atestação falhar, o servidor enviará uma mensagem de falha de atestação e o cliente imprimirá a
mensagem “ATTESTATION FAILED”. Se a atestação for bem-sucedida, o servidor enviará uma
mensagem de sucesso e o cliente imprimirá a mensagem “ATTESTATION OK”.
Após a verificação da atestação da SpertaClient, o utilizador autentica-se no servidor. Caso um
utilizador se tente autenticar, e não esteja registado no servidor, o Servidor fará o registo do novo
utilizador, adicionando o user-id e a respetiva password ao ficheiro de utilizadores do servidor. Devem
também ser inicializadas as estruturas de dados que mantêm a informação relativa a cada utilizador.
Quando um utilizador cria uma casa, o servidor cria a estrutura da Fig 2 para a nova casa, onde cada
seção contém um contador iniciado a 1. Assim, cada vez que o comando RD <hm> <s> é usado para
registar um dispositivo numa dada seção <s> de uma casa <hm> (ex., RD Casa1 P), o contador associado
àquela seção, daquela casa é incrementado, e consequentemente, o dispositivo é criado e registado no ficheiro
da casa. Esta estrutura e contadores terá de ser mantida num ficheiro de texto para manter a informação de
contadores.
